# 版本与兼容

编译器用 `v0.MINOR.PATCH` 三段版本号，`nf version` 打印当前这一版。这一页说明三位数各自在什么时候变、`0.x` 阶段承诺什么、升到 `1.0.0` 还差什么。每一版改了什么，记在仓库根的 `CHANGELOG.md`。

版本号只说改动，不说计划。

## 三位数各自什么时候变

| 升哪一位 | 什么时候变 | 已经发生过的一次 |
| --- | --- | --- |
| `PATCH`（`v0.4.2`） | 只修缺陷：能写出的程序不变，报错的文字也不变 | 实参达到五个时，生成的代码会写坏自己那一份清理信息，程序可能崩溃；这一处修掉时，能写出的程序没有变，合在 `v0.3.1` 里发出去 |
| `MINOR`（`v0.5.0`） | 语言行为变了一轮：能写出以前写不出的程序，或者某条报错改了说法 | `v0.4.0` 多了 `ref` 这个记号，参数前面写 `ref` 就是只读借用，另外多出七句报错原文 |
| 升到 `1.0.0` | 下面三个条件全部达到，缺一条就不算 | — |

## `0.x` 阶段不承诺向后兼容

`v0` 这一档里，每一次 `MINOR` 都可能改动语言行为：以前能通过检查的写法可以变成错误，一句报错的说法也可以换掉。

要固定行为，就把编译器的版本号写进自己的构建脚本里，用 `nf version` 对照。

一句报错改了说法，也算语言行为变了一轮，版本号至少升 `MINOR`。

每句报错都在仓库里的一张表上逐句比对（`compiler/testdata/报错文字.txt`），改一个字检查就失败。[错误信息索引](/tools/060_errors)收录的就是这批原文。

## 升到 `1.0.0` 的三个条件

1. **语言的规则逐条定下。** 从基础类型、语句、函数到容器与错误处理，每一条规则都已经写定，改动它要先有一条新的决定跟上。和可执行文件格式、后端实现有关的那几条有意不写死：换平台、换可执行文件格式一定要改动它们，写死了反而妨碍跨平台；规则还没补全的那一小部分也照实留着。
2. **每句报错都有表逐句比对。** 前面说的那张表已经做到：改动一句报错原文，检查当场失败。
3. **至少有一个不是这套工具自己写的程序，在这套工具链上运行。** 这一条要等对外发布之后才会出现。

## 怎么确认手上是哪一版

```text
nf version
```

开发用的构建打印 `nf dev`；带版本号的构建打印 `nf v0.4.1` 这一种。打印出 `nf dev` 只说明这份构建没有注入版本号，不代表编译器有额外的改动。

VS Code 插件与编译器同号发布：插件的 `0.4.1` 对应的就是编译器的 `v0.4.1`，同一轮的语言改动两边一起走。

插件自带的那份编译器在打包时现编，注入的就是插件自己的版本号，所以在编辑器里跑 `nf version` 得到的也是 `nf v0.4.1`。用法与安装写在[编辑器与调试](/tools/061_editors)。
