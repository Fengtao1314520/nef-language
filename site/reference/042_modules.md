# 多个文件

一个程序可以拆成多个 `.nf` 文件。

命令行指定的文件是入口，其余文件由 `import` 引入。

## import

```nf
// util.nf
export method helper(n:int):int { return n * 2 }

method only_here():int { return 1 }      // 别的文件 import 了也拿不到
```

```nf
// main.nf
import { helper } from "./util.nf"

console.print(helper(3))   // 6
```

| 事项 | 规则 |
| --- | --- |
| 写法 | 工程里的文件之间只有一种写法：用花括号列出名称，`from` 后面写一条相对路径。引入一整个包是另一种写法，见下面“包”一节。没有 `import * as`，没有只写一句 `import "./x.nf"`，也没有 `export default` |
| 路径 | 要带 `.nf` 后缀。以 `./` 或 `../` 开头的写法按**书写该语句的文件**所在目录解析，与执行命令时所在的目录无关，这是推荐写法。不带前缀时也能通过检查，这时路径按字面解析，也就是按**执行命令时所在的目录**解析；同一份工程换一个目录运行就会找不到文件，不要使用不带前缀的写法 |
| 分隔符 | 只接受 `/`，Windows 上也这么写（`\` 在字符串里是转义记号） |
| 大小写 | 编译器只是把路径拼成一个字符串，能否打开由文件系统决定，编译器不核对大小写。Windows 的文件系统不区分大小写，所以在当前 Windows 上大小写不影响结果；换到区分大小写的系统上，多一个大写字母就会报文件找不到 |
| 名称 | 花括号里的每个名称都必须是目标文件 `export` 过的；引入没有导出的名称是编译错误，文件找不到也是编译错误 |
| 改名 | `import { helper as h } from "./util.nf"`，之后本文件内只使用 `h` |
| 重复引用 | 同一个文件被两条路径引入，只执行一次 |
| 互相引用 | 是编译错误，要求把共用的部分移到第三个文件 |
| 引入未使用 | 花括号里列出的名称只要有一个在本文件里没有被使用，编译器就报错。标准库的十四个组名不适用这条检查 |

工程里的文件共用一个名称空间：两份文件各写一个同名定义就是编译错误，报的是 `Pair 已经定义过了` 或 `函数 make 重复定义：一个名字只能有一个`。`as` 改的只是本文件里的写法，重名发生在定义处，改名解决不了。

把名称隔开的是包：每个包的名称只属于这个包，两个包各有一个 `Pair` 不算重名（见下面“包”一节）。也不允许后引入的名称替换先引入的名称。

## export

写上 `export` 才算对外导出。没有写 `export` 的定义只在本文件内可见。

可以对外导出的定义有六种：`method`、`struct`、`class`、`interface`、`enum`、`const`。

顶层的 `let` 不能 `export`：它是本文件内的名称，别的文件读不到。

`export const` 导出的是一个改不动的值：任何文件引入之后都只能读取，写入它是编译错误。要让几个文件共用同一个**可变的**值，只有下面 `shared` 这一种写法。

```nf-bad
export let count:int = 0     // 报：顶层的 let 不能 export：跨文件共用一份可变的要写 export shared
```

## 顶层语句在哪跑

每个文件的顶层都会执行一次，包括被 `import` 引入的文件。

被引入的先执行，入口文件最后执行；同一个文件被两条路径引入，也只执行一次。

依赖的先后顺序总能确定：互相引用本身就是编译错误。

所以在被引入的文件顶层写 `let count:int = 0` 是有意义的：这条初始化语句在程序启动时执行一次，`count` 之后供本文件的函数使用，但它不能给别的文件使用。

顶层也是一个作用域。`let`、`const` 都能写在顶层，顶层的值按声明的反序释放。`const` 只能与值类型搭配。

只有一处与函数体不同：顶层的值要到**整个程序执行结束**才释放。为什么要这样设计、各文件的顶层按什么次序向前释放、`export shared` 为什么不参与，都写在[值与存放](/reference/038_memory)。

`args` 是例外。它是入口文件顶层预置的名称，只有入口文件的顶层能写，别的文件里写 `args` 是编译错误。

别的文件要使用命令行参数，就从入口文件把需要的值传进去。

`console.print(args)`、`length(args)` 这类调用是只读借用；把 `args` 当实参传给自己写的函数就是交出，这个名字此后不能再使用。

## 定义的先后不算顺序

一个文件里的顶层定义不分先后，`import` 引入的名称同样如此。

编译器先收集全部顶层名称，再检查调用。入口文件的顶层语句按书写顺序执行，所以调用写在后面的函数没有问题。

## 标准库不用 import

十四个组名在任何文件里直接书写就能使用。

不需要 `import`，也无法 `export`：`console`、`text`、`number`、`math`、`time`、`file`、`path`、`environment`、`regular_expression`、`json`、`bytes`。

## export shared

要让几个文件共用一份可变的值，就写 `shared`。

加上这个标注，就等于承认这份数据有好几个文件在读写，而没有任何一个文件独占它。

```nf
// registry.nf
export shared bag:list<string> = []

export method note(entry:string) {
    bag.add(entry)
}
```

```nf
// main.nf
import { bag, note } from "./registry.nf"

note("书包")
console.print(length(bag), bag[0])   // 1 书包
```

| 事项 | 规则 |
| --- | --- |
| 写法 | `export shared` 必须成对书写，只能出现在顶层。单独一个 `shared` 是编译错误：不导出的共享没有意义，本文件的 `let` 就够了 |
| 生命周期 | 不参与释放。程序启动时随本文件的顶层初始化一次，存活到进程结束 |
| 交出 | 不可以。`eat(bag)`、`let x = bag`、`return bag`、`box.add(bag)`、`bag as object` 全是编译错误：交出去就意味着全局名称被取空，而别的文件还在使用同一个值。只能就地读写 |
| 容器里的元素 | 照常按每个位置只保存一份处理：`let s:string = bag[0]` 读走该位置上的文本，这个位置此后是 `null`。共用的是这个容器，不是里面每个元素的归属 |

`shared` 不限制类型。`export shared count:int = 0` 合法，读写这个值就像读写一个普通的静态变量，几个文件修改的是同一个值；`string`、`enum`、`class` 与三种容器都可以标注。

标注 `const` 而不标注 `shared`，每个文件各自持有一个改不动的值；标注 `shared`，各文件使用同一个可变的值。

使用 `shared` 而不是 `let`，是为了向读代码的人标明：这个值有好几个文件在修改。

## 包

要把自己写好的一组源文件分发给别人使用，就打包成一个 `.nfpack` 文件：`nf pack greet.nf -o libs/greet.nfpack`。

包文件里装的是这个包的源文件，使用者把它放进自己工程的 `libs/` 目录就能引入，全程不联网，也没有中央仓库。打包的规则写在[命令行工具](/tools/059_cli)。

```text
import greet from "libs/greet"

let p:greet.Pair = greet.make()
console.print(p.left, greet.twice(21))
```

引入包时把整个包绑定到一个名称上，取包里的成员一律写 `包名.成员` 这种形式。绑定哪个名称由引入的一方决定，所以这个名称不能与本文件里已有的名称重复，也不能是标准库列出的十四个组名。

包里引入自己的依赖，写的也是同一种语句：`import shout from "libs/shout"`，取包里的成员写 `shout.shoutOnce(name)`。这个依赖在打包时已经被装进包文件，使用者不需要再安装一遍。

包里 `export` 过的成员才能被包外使用。每个包对外的入口文件叫门面文件，名称按约定是 `<包名>.nf`。

| 事项 | 规则 |
| --- | --- |
| 版本 | 版本写死在 `nf.json` 里：不比较大小、不写范围、不挑版本。工程的 `nf.json` 与包文件里的那份对不上时是编译错误 |
| 包内与包外 | 用花括号列出名称的写法不能引入包内的文件；包里的文件也只能使用本包的名称和自己引入的包，看不到工程的名称。同一个包换一个工程也要照样能编译 |
| 同名的两份包 | 允许并存：两个包各有一个 `Pair`、同一个包的两份版本各自被别的包引入一份，都不算重名。包不同，这两个类型就是两个不同的类型，值不能互相传入 |
| 门面导出的类型 | 只能是这个包自己定义的类型：参数、返回值、字段、别名都算。依赖在包文件里面，包外面写不出这种类型的名称 |

## `nf.json` 的字段

工程根与包各写一份 `nf.json`，两份用的是同一组字段，读法不同。

| 字段 | 写什么 | 工程根那一份 | 包那一份 |
| --- | --- | --- | --- |
| `name` | 这个包叫什么 | 不读 | 必填，而且要跟门面文件的名字一致 |
| `version` | 这一版是几号 | 不读 | 必填 |
| `deps` | 包名对应哪一版 | 直接引的每个包写一版 | 本包直接用的每个依赖写一版 |

三份位置各有各的用处：

- 工程根那一份只读 `deps`：`import shout from "libs/shout"` 要哪一版，就从这里取。工程根没有这份文件时，`libs/` 里放着哪一版就用哪一版。
- 包那一份放在门面文件旁边，`nf pack` 从这里取名字、版本与依赖。缺 `name` 或缺 `version`，打包这一步就报错。
- 依赖被并进容器之后，它所在的那一层目录里也带一份 `nf.json`（`pkg/依赖名/版本/nf.json`），它自己要的依赖从那里读。

`deps` 的值是一个版本号字符串，不是范围：写 `"2.0"` 就是要 `2.0`，旁边那份是 `1.4` 时报错，不会替挑选一个版本。

## 命令

命令行只接受**一个入口文件**：`nf hello.nf 甲 乙`（在内存里编译完成后直接运行）、`nf build hello.nf [-o tool.exe]`（生成独立产物）、`nf check hello.nf`（只执行前端检查，报错带上文件、行号与列号）。

多文件工程里这三条命令都只指定入口文件的文件名，其余文件由 `import` 引入，不需要逐个列在命令里。九个子命令的完整分工与退出码写在[命令行工具](/tools/059_cli)。

产物可以直接运行，机器上不需要安装 `nf`，也不需要任何运行时。
