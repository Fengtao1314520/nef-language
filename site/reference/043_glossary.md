## 先把程序跑起来

**编译期与运行期（compile time / run time）**

- 通俗定义：编译期是 `nf` 读源文件并生成机器码的阶段，运行期是产物开始执行的阶段。
- 常见误区：以为类型对不上要等到程序运行到那一行才发现。这类问题在编译期就报出来，程序根本不会开始运行。
- 别的语言里：和 Go、Rust 一样，类型错在编译期就报；Python 的类型问题多数要到运行时才暴露，需要用 mypy 这类工具提前检查。

**类型标注（type annotation）**

- 通俗定义：写在名称后面的类型，`let total:int = 0` 里的 `int`。
- 常见误区：以为不写也行，以为编译器会根据右边的初始值推导。变量、参数、返回值、字段四处都得写，一处都不推导。
- 别的语言里：Rust 的 `let` 也要求标注，但能从初始值推导；Go 的 `:=` 一律推导；TypeScript 可以全部省略。Nef 一处都不推导，标注是语法的一部分。

**字面量（literal）**

- 通俗定义：代码里直接写死的值，例如 `0`、`3.5`、`"书包"`、`[1, 2]`。
- 常见误区：以为 `0644` 是八进制、`1e5` 是科学计数法。这两种写法都不支持，是编译错误；`1_000_000` 与 `0xFF` 可以写。
- 别的语言里：`_` 分组和 `0x` 与 Java、JavaScript、Rust 的写法一致；C 与 Go 还支持八进制 `0644`，Nef 没有这一种；小数不支持科学计数法，写法比 Go 和 Rust 都少。

**零值（zero value）**

- 通俗定义：每个类型都有的默认值：`false`、`0`、`0.0`、码点 `0`、`null`。
- 常见误区：以为没赋过值的字段是“未定义”。字段有零值，读得到，只是未必是期待的那个值。
- 别的语言里：Go 的包级变量和字段同样是零值，这一点最接近；C 与 C++ 的局部变量不初始化就是内存里的残留；Rust 直接拒绝读未初始化的值。

**产物（executable）**

- 通俗定义：`nf build hello.nf` 生成的可执行文件，双击就能运行。
- 常见误区：以为拿到产物的人还要额外安装什么。不需要运行时，也不附带垃圾回收器。
- 别的语言里：和 Go 的 `go build` 一样，产出一个静态文件，拷过去就能运行；Java 要带上 JVM，Python 要带上解释器。

## 值有两种存放方式

**值类型（value type）**

- 通俗定义：`boolean`、`int`、`float`、`byte`、`unicode`、`struct`、`enum` 这几类，赋值是整份拷贝，两份拷贝互不影响。`struct` 也属于值类型，但名称里放的是 8 字节的句柄、正文在堆上，拷贝时连堆上那块数据一起复制。
- 常见误区：以为 `struct` 赋值是传一个指针。实际是整份拷贝，字段里再嵌一层 `struct` 也一起拷下去。
- 别的语言里：对应 C 的 `struct`、C# 的 `struct`、Rust 里实现了 `Copy` 的类型。Java 只有 `int` 这类原始类型是值，对象一律引用。

**引用类型（reference type）**

- 通俗定义：`string`、`object`、`class`、三种容器，还有 `Json` 与 `bytes` 这两种内建类型。名称里存放的是一个句柄，指向堆上的值。
- 常见误区：以为赋值会复制一份内容。赋值只是把句柄交出，原来的名称当场失效。
- 别的语言里：Java、C#、Python 的变量存的也是引用，但赋值会再复制一份引用，两个名字都能用；Rust 的 `String` 赋值才会让原名字失效，这一点与 Nef 相同。

**不可变（immutable）**

- 通俗定义：`string` 建好之后内容不会变；`s + t`、`s.slice(0, 3)` 返回的都是新的文本。
- 常见误区：以为 `s[0]` 能被改写。下标只读，写它是编译错误。
- 别的语言里：Java、Go、Python 的文本同样不可变；C 的 `char*` 缓冲区可以就地修改，Rust 的 `String` 加了 `mut` 就能就地修改，Nef 没有这种写法。

**码点（code point）**

- 通俗定义：`unicode` 这个类型保存一个字符，占 4 字节；`string` 是码点排成的一串。
- 常见误区：以为一个汉字占三个下标位置。`length(s)` 统计的是码点个数，`s[i]` 取的也是一个码点，与 UTF-8 的字节数无关。
- 别的语言里：Python 3 与 C# 的下标按码点计数（严格说是 UTF-16 单元）；Go 的 `s[i]` 取的是字节，统计码点要用 `utf8.RuneCountInString`；Rust 的 `String` 干脆不支持按下标取。

## 一个值只有一个持有者

**所有权（ownership）**

- 通俗定义：同一个时刻，一个值只有一个持有者。能决定这个值什么时候释放的名称，就是持有者。
- 常见误区：以为持有者就是最早声明这个值的那个名称。持有者随交出转移，与最早那句 `let` 无关。
- 别的语言里：Rust 的 ownership 是同一套思路；C++ 靠约定和智能指针；Go、Java、Python 不追踪归属，释放由垃圾回收器负责。

**交出（move）**

- 通俗定义：赋值、传实参（参数没写 `ref` 时）、`return`、装进容器、装箱，这五种操作都是交出：交出的是值的持有者身份，原来的名称失效。
- 常见误区：以为调用标准库也会把值交出。`items.add(x)` 里的 `items` 是只读借用，持有者没变；装进去的那个 `x` 才归容器所有。
- 别的语言里：Rust 的 move 与这里的交出几乎逐字对应（`let b = a;` 之后 `a` 不能再用）；Go 与 Java 的赋值只复制引用，没有“原名字失效”。

**只读借用（read-only borrow）**

- 通俗定义：四处只读借用：`for (w:string in words)` 里的 `w`、标准库函数的接收者（点号左边的容器）、方法体里的 `this`、参数前标了 `ref` 的位置。这四处都在[值与存放](/reference/038_memory)里逐条列出。
- 常见误区：以为借用是一份拷贝，或者以为能把借来的值留下来。`let d:C = c`、`return c` 都是编译错误，出了所在的作用域，借用同样失效。
- 别的语言里：对应 Rust 的 `&T`；Go、Java 传对象时拿到的是可以修改的引用，C++ 的 `const&` 更接近一些。

**句柄（handle）**

- 通俗定义：操作系统给出的一个编号，不是内存里的一块区域。当前有三种句柄：一条 TCP 连接的 `Socket`、本机监听的 `Listener`（[TCP 套接字](/stdlib/057_net)），以及自己启动的进程 `Process`（[进程](/stdlib/053_process)）。句柄同样只有一个持有者，名称失效时执行的是关闭这个编号，不归还内存；`Process` 关闭时，会先结束那些还没等待过的子进程。
- 常见误区：以为句柄能像 `bytes` 那样装进容器。装不进去：容器析构时要整体释放里面的每个值，而一个操作系统句柄只能关闭一次，两个名称指向同一个值就会关闭两次。
- 别的语言里：C# 的 `SafeHandle`、Go 的 `net.Conn` 都负责关闭句柄，只是它们靠 finalizer 或 `defer` 来关；Nef 把关闭动作放在名称失效这一步，与其他资源的释放时机相同。

**作用域（scope）**

- 通俗定义：`{}` 括起来的范围；在里面声明的名称，出了这个范围就失效。
- 常见误区：以为 `if` 块里声明的名称在块外面还能用。不能。
- 别的语言里：边界与 C、Go、Rust 一致。差别在遮蔽：C、Go、Rust 都允许内层再声明一个同名名称，Nef 直接报“与外层的名字重名”。

**析构（destruct）**

- 通俗定义：释放一个值占用的内存，以及它持有的内存块。作用域结束、`return`、`exit`、程序结束时，都会执行。
- 常见误区：以为要自己写释放，或者有一个回收器在背后收垃圾。没有，编译器在每一处离开作用域前生成一段释放内存的调用。
- 别的语言里：Rust 的 `Drop` 与 C++ 的 RAII 是同一时机；Go 的 `defer`、Python 的 `with` 要自己写出来；Java 的 `finally` 也是。

**悬垂引用（dangling reference）**

- 通俗定义：变量里的句柄指向已经释放的值。
- 常见误区：以为要到运行时才会发现。这门语言在编译期就拒绝“值已经释放、句柄还在使用”的写法。
- 别的语言里：C 与 C++ 不查，运行期才出问题（读到已释放的内存）；Rust 靠借用检查器在编译期拒绝，与 Nef 同一条路。

**双重释放（double free）**

- 通俗定义：同一块内存被释放两次，第二次释放的是别人正在使用的内存。
- 常见误区：以为两个名字都能释放。一个值只有一个持有者，所以这种情况在源头就不会出现，编译期直接报错。
- 别的语言里：C 里是最常见的崩溃原因之一；Rust 靠所有权从源头杜绝；Go、Java 有垃圾回收，不存在手工释放。

## 容器

**容器（container）**

- 通俗定义：三种内建的可变长容器：`list`（有序可重复）、`dict`（键到值）、`hashset`（去重、只判断存不存在）。
- 常见误区：以为长度写成 `a.length`。写 `length(a)`，它是函数。空的 `{}` 是 `dict` 还是 `hashset`，看左边的类型标注。
- 别的语言里：大致对应 Go 的 slice 与 map、Rust 的 `Vec` 与 `HashSet`、Python 的 `list` 与 `dict`。差别在长度：Go 是 `len(x)` 函数，Rust 与 Python 是方法。

**元素与键（element / key）**

- 通俗定义：容器里存放的每一项叫元素；`dict` 中用来定位元素的那个值叫键。
- 常见误区：以为读一个不存在的键会给零值。读取时抛出 10032 号错误，写入一个不存在的键才是新增一条记录。`dict` 与 `hashset` 的遍历不保证顺序。
- 别的语言里：Python 读缺失键抛 `KeyError`，最接近；Go 读缺失键返回该类型的零值，Rust 的 `HashMap::get` 返回 `Option`，要靠 `?` 或 `unwrap`。

**读走（read out）**

- 通俗定义：读一个下标就是交出：`let x:string = items[0]` 之后，`items[0]` 那一处变成 `null`。`class` 的字段装着引用类型时同样如此：`let a:Inner = o.i` 之后 `o.i` 返回 `null`。只是顺着读一下不算交出（`console.print(o.i.v)`），这样的读不会产生新持有者。
- 常见误区：以为读一下不损失什么。一个位置只保存一份值，要留住就得自己用一个名称接住；同一个位置要再取一次，得先判断它是不是 `null`。
- 别的语言里：这一条没有对应说法：Go、Java、Python 读下标不损失容器里的内容；Rust 想移出一个元素要写 `Vec::remove(i)` 或 `swap_remove(i)`，读和移是两个动作。

## 自己定类型

**装箱（boxing）**

- 通俗定义：`x as object`，把值放进一个能装任何类型的盒子里，一次堆分配。
- 常见误区：以为 `string`、容器与 `Json` 也能装进盒子。进得去的只有 `class`、`struct` 与值类型，这三类都在检查阶段就被拒绝：文本收到的是“串与非串之间不走 `as`”，容器与 `Json` 收到的是“`list<int>` 装不进盒子：盒子只装 class、struct 和值类型，要混装就一个一个装进去”。要放一段文本，先把它包进一个 `class`。
- 别的语言里：Java 与 C# 是自动装箱，写 `Object o = 42;` 就发生了；Rust 要显式 `Box::new(v)`；Nef 必须写 `as object`，不提供自动装箱。

**拆箱（unboxing）**

- 通俗定义：`o as int`，把盒子里的值取回来；`o is int` 先问它装的是不是某个类型。
- 常见误区：以为类型不符会给 `null`。它当场抛 10011 号，能 `catch`，没有“失败给空”的温和版本。拆完盒子就空了，原来的名称也交不出值。`as` 的右边写成容器或 `Json` 是编译错误：它们从来没进过盒子，也就拆不出来。
- 别的语言里：Java 的向下转型失败抛 `ClassCastException`，C# 抛 `InvalidCastException`，形状最接近；Rust 的 `downcast` 给 `Result`，Python 的 `isinstance` 对应这里的 `is`。

**`struct`（值类型自定义）**

- 通俗定义：几个字段打包成一个值类型，写在顶层，`Point { x: 1, y: 2 }` 造出来。
- 常见误区：以为字段里能放 `class` 或容器。只能放值类型、`string` 与另一个 `struct`。
- 别的语言里：与 C# 的 `struct`、Rust 的 struct 同一类东西；Go 的 `struct` 是值类型但字段什么都能放，Java 没有对应的记录类型（`record` 仍是对象）。

**`class`（引用类型自定义）**

- 通俗定义：写在顶层的引用类型，`new` 一个出来，字段可以放任何类型，包括容器。
- 常见误区：以为它能继承另一个 `class`。`base` 后面只能跟一个 `interface`。
- 别的语言里：字段加方法的组织方式与 Java、C# 相同；不能继承别的类这一点更接近 Go：Go 没有类继承，只有组合与接口。

**`interface`（接口）**

- 通俗定义：对“必须有哪几个字段、哪几个方法”的约束，`struct` 与 `class` 用 `base` 接过去。
- 常见误区：以为接口名称能当类型写。不能。混装一组实现同一接口的对象，只能用 `list<object>` 装入，取出来再用 `is` 判断类型、用 `as` 拆箱。方法声明里不写 `method`，每一个都必须实现，参数名也要完全相同。
- 别的语言里：Go 的接口是隐式满足，不写任何声明；Java、C# 要写 `implements`；Nef 用 `base` 显式声明，但接口名不能出现在类型位置上，比这三者都更窄。

**`enum`（枚举）**

- 通俗定义：给几个整数各起一个名字。
- 常见误区：以为它能参与算术、能从整数转回来。只有一个单向的转换：`D.x as int` 取出成员对应的那个整数，它的作用就是给错误码起名。
- 别的语言里：形状像 C 的 `enum`，但没有算术，也不能从整数转回来；Rust 与 Swift 的枚举可以带数据，Java 的枚举可以有方法，这里都没有。

**`null`（空引用）**

- 通俗定义：一个引用暂时没有指向任何东西。
- 常见误区：以为它是一种类型、或者能当“假值”用。它是值不是类型，只能写在引用类型的声明与赋值右边，只能跟引用类型比 `==` 与 `!=`；拿它跟值类型比较，或者用它比较大小，都是编译错误。条件位置只收 `boolean`。
- 别的语言里：Java、C# 的 `null` 与 Go 的 `nil` 用法最接近；Python 的 `None` 常当假值用，Nef 没有真值语义；Rust 没有 `null`，用 `Option<T>` 表达“可能没有”。

## 出错与拆开文件

**抛出与捕获（throw / catch）**

- 通俗定义：失败用异常传递。`throw (100, "路径不能是空的")` 抛，`try` 与 `catch (code, msg)` 接。
- 常见误区：以为函数签名上要标它可能抛什么。什么都不标，也没有 `finally`；`catch` 不筛选错误码，任何错误码都由它接住。
- 别的语言里：比 Java、C# 简单一档：那里的 catch 按异常类型分支，还有 `finally`；Go 用 `error` 返回值加 `panic`/`recover`；Rust 用 `Result` 加 `?`。

**内建错误码（built-in error code）**

- 通俗定义：语言自己那批错误码占 `10000` 往上：溢出 21、除以 0 是 22、下标越界 31、`dict` 没有这个键 32、拆箱类型对不上 11、拿着 `null` 取成员 92，文件路径那几组往后排。
- 常见误区：以为整数溢出会绕回去、除 0 给无穷。两者都当场抛出，形状和手写 `throw` 完全相同，能 `catch`。要抛别的错误就自己写 `throw`，错误码写在 `0` 到 `9999`。
- 别的语言里：C 与 Go 的整数溢出静默回绕，Java 同样静默回绕（`Math.addExact` 才报）；Rust 在 debug 下 panic；除 0 在 Go 与 Java 是运行期崩溃，Python 抛 `ZeroDivisionError`；能捕获这一点与这里最接近的正是 Python。

**退出码（exit code）**

- 通俗定义：程序运行结束返回给操作系统的整数。正常执行到最后是 `0`，`exit(n)` 返回 `n`，没有被捕获的抛出会打印一行，然后返回 `1`。
- 常见误区：把错误码当退出码。10041 号“文件读不到”被 `catch` 接住之后，程序仍然可以正常结束，返回 0。
- 别的语言里：与所有语言一致：C 从 `main` 里 `return` 返回值、Go 的 `os.Exit`、Python 的 `sys.exit`。差别只有一条：`10000` 往上那批错误码不参与退出，程序自己的退出码写在 `0` 到 `9999`。

**顶层（top level）**

- 通俗定义：文件里不属于任何函数体的顶层语句，从上到下依次执行；一个程序没有入口函数。
- 常见误区：以为要写 `main`。命令行指定的那个文件就是入口，其余文件由 `import` 引入，它们的顶层也各执行一次，先执行被引用的文件。
- 别的语言里：Python、JavaScript、shell 就是这样；Go 的顶层只能写声明和 `init` 函数，可执行语句必须在函数里；C、Java、Rust 都要一个入口函数。

**`import`、`export`、`shared`**

- 通俗定义：`export` 表示这个名字对外可见，`import { helper } from "./util.nf"` 是把别的文件导出的名称引入本文件；`export shared` 是把一份可变的值交给几个文件共用的写法。
- 常见误区：以为花括号那种写法也能引用包内的文件。花括号只能引用本工程的 `.nf` 文件，路径以 `./` 或 `../` 开头；`libs/` 里的包整块引入（见下面“包”那一节）。路径怎么解析、大小写算不算，写在[多个文件](/reference/042_modules)；两个文件互相引用是编译错误；`shared` 声明的值不能交出，只能就地读写。
- 别的语言里：写法接近 JavaScript 与 TypeScript 的具名 `import` 与 `export`，但路径必须自己写相对形式和后缀；C# 的 `using` 引的是同一个工程里的名字空间，也不从目录里挑文件。

**包（package）**

- 通俗定义：一个人写好的多个 `.nf` 文件打成的一个文件，后缀 `.nfpack`。放进自己工程的 `libs/` 目录就能引入：`import greet from "libs/greet"`，取里面的成员一律写 `greet.make()`。
- 常见误区：以为安装要联网、有一个中央仓库。没有：安装就是把那一份文件复制到 `libs/` 目录里。也以为两份同名的包放在一起会重名报错：它们可以在同一个程序里并存，各归各的包，但那是两个不同的类型，值不能互相传入。
- 别的语言里：用法像 JavaScript 里给一个模块挂命名空间再点点号；分发像 C# 的 NuGet：把做好的包交给别人使用。Nef 没有在线仓库，版本写死在 `nf.json` 里，不比较大小，也不挑版本。

**门面（façade）**

- 通俗定义：一个包对外提供的唯一入口文件，名称按约定是 `<包名>.nf`。它 `export` 了什么，外面才取得到什么；包里的其余文件在包文件内部，外面看不见它们的名称。
- 常见误区：以为门面上想返回什么类型都行。它导出的类型只能是这个包自己定义的：把依赖里的类型写进返回值，使用这个包的人说不出那个类型的名称，所以这种写法在编译期就被拒绝。
- 别的语言里：像 C# 项目里只把 `public` 成员给外面、内部类型留 `internal`；JavaScript 的包靠 `package.json` 的 `main` 字段指定入口文件，Nef 靠的是文件名约定。
