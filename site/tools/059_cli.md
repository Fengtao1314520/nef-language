# 命令行工具

工具链只有一个可执行文件 `nf`，共九个子命令。这一页说明三件事：每个命令怎么写、退出码代表什么、消息走标准输出还是标准错误。

| 命令 | 作用 | 退出码 |
| --- | --- | --- |
| `nf check 文件.nf` | 只做词法、语法、类型与归属检查，不生成也不执行 | 通过 `0`，不通过 `1` |
| `nf 文件.nf 参数…` | 在内存里完成整个编译过程后直接执行，不写入中间文件 | 程序的退出码 |
| `nf build 文件.nf [-o 产物名]`、`nf pack 门面.nf [-o 容器名]` | `build` 生成独立可执行文件；`pack` 把一个包的源文件合并成一份 `.nfpack`，供其他人使用，不生成可执行文件、也不执行代码 | 成功 `0`，失败 `1` |
| `nf tokens 文件.nf`、`nf ir 文件.nf` | 打印分析的结果：记号流逐行打印一个记号，中间码逐行打印一条指令。两个命令都不生成机器码，也不写入文件 | 成功 `0`，前端未通过 `1` |
| `nf lsp`、`nf dap`、`nf version` | 前两个命令供编辑器使用：`lsp` 从标准输入读取请求、向标准输出写回带行列的报错，同时回答补全候选与悬停说明；`dap` 使用同样的两条流，返回的是断点、单步与变量信息，检查用的规则与 `nf check` 相同；`version` 打印编译器自身的版本号，脚本可以用它判断本机是否已安装 | 正常退出 `0`；标准输入输出通道读取失败时 `1` |

命令行没有给出参数，或者给出无法识别的子命令时，标准错误上打印一行用法提示，退出码 `2`。

## `nf check`

```text
nf check hello.nf
```

通过时标准输出上是一行 `检查通过：1 个文件`；这个数字是本次实际读取的文件数，包括 `import` 引入的文件。

编译器的消息走标准错误。

程序自己的输出走标准输出。

两条流分开接收，脚本处理时就不会互相干扰。程序自己打印的错误消息也算程序自己的输出，见下面“程序的退出码”。

不通过时，报错的形式取决于问题出在哪个阶段，共有两种。

词法或语法没有通过时，标准错误上只有最先出现的一条报错，依次给出文件名、第 N 行第 M 列与一句消息；报完这一条就返回，不再检查后面的问题，也没有汇总行；修正一句才看见下一句。

静态检查阶段一次列出所有问题，一句一行走标准错误，最后追加一行 `共 N 处不对`：

```text
hello.nf 第 1 行第 5 列：声明 a 必须标类型
共 1 处不对
```

多条问题按整行文字排序，同一次运行里的先后顺序稳定。行号只是这串文字的一部分，比较时按字符而不是按数值，所以第 10 行排在第 2 行前面。

> 注意：`nf check` 做完前端各阶段就停止，不生成机器码。通过检查不等于能生成产物，见下面“生成阶段的边界”。

## 直接运行

```text
nf hello.nf 甲 乙
```

编译在内存里完成，接着执行，不写入任何中间文件。命令行上脚本名之后的参数进入程序顶层的 `args`（`list<string>`），`args[0]` 就是第一个参数。

屏幕上看到的就是程序自己的输出，退出码同样是程序自己的退出码。

## `nf build`

```text
nf build hello.nf
nf build hello.nf -o tally.exe
```

没有 `-o` 时，产物与源文件同名、同目录。产物是独立可执行文件：运行它不需要本机安装 `nf`，也不需要任何运行时；它只向操作系统请求三项服务：写文件、申请内存、退出。

`import` 引入的文件会一起编译进去，不需要额外参数。

## `nf pack`

```text
nf pack greet.nf
nf pack greet.nf -o libs/greet.nfpack
```

这个命令的产物是一个包：把一个人写好的一套 `.nf` 文件合并成一份 `greet.nfpack`，使用者拿到的是一个文件，而不是分散的多个源文件。

包名就是门面文件的名字，`greet.nf` 这个包叫 `greet`。名称、版本与所用依赖都写在门面文件旁边的 `nf.json` 里：

```text
{
  "name": "greet",
  "version": "1.0",
  "deps": { "shout": "2.0" }
}
```

门面里以 `./` 开头的引入指向这个包自己的文件，会一起包含在包内。整块引入的写法（`import shout from "libs/shout"`）指向本包使用的依赖，从包旁边的 `libs/` 目录里读取。

包里用花括号指向 `libs/` 的写法会被拒绝：花括号写法只用于引入工程里的文件，路径必须以 `./` 或 `../` 开头。这个错误在打包阶段就报出来，不会生成一份其他人编译不过的容器。

依赖自己引入的依赖也一并合入，放在容器内 `pkg/依赖名/版本/` 目录下；两个依赖指向同一个包时不重复合入。

打包出来的文件不压缩，里面的字节与磁盘上的源文件完全一致，行号与列号在容器里的副本上同样适用。

这条命令不生成可执行文件，也不执行任何代码。打包失败时退出码 `1`，标准错误上的消息会指出具体是哪个文件、哪个位置对不上。

门面文件的名字与 `nf.json` 里的 `name` 不一致，或者缺少 `version`，都在打包这一步报出。

引入了依赖却没有在 `deps` 里写明版本，或者指定的版本与旁边目录里已有的版本不一致，同样在这一步报出。

## 词法记号：`nf tokens`

`nf tokens 文件.nf` 每行打印一个记号，格式是 `类别:文本`。类别有 `nl`（行尾）、`name`（标识符与关键字）、`num`、`str`、`char`、`op`；行尾的文本打印成 `\n`，结尾的 `eof` 不打印。

```text
nf tokens demo.nf
```

```text
name:let
name:a
op::
name:int
op:=
num:1
nl:\n
```

对应的输入是一行 `let a:int = 1`。

这个命令通常在两种情况下使用：某个写法被误判，需要确认词法分析把它拆成了哪些记号；或者要确认 `1e5`、`0644` 这类字面量被解析成了什么。词法分析本身失败时，输出是一行“第 N 行第 M 列：消息”，退出码 `1`。

## 中间码：`nf ir`

`nf ir 文件.nf` 完成检查与降级就停止，把中间码输出到标准输出，不在磁盘上留下任何文件。

每行一条三地址指令。`%1 = @0 + 2 :: int` 里 `%N` 是本帧的槽，`@N` 是静态槽（顶层的名字与 `args`），`$N` 是文本池里的第 N 段。`_ = call` 表示这次调用不写目标。

```text
nf ir demo.nf
```

```text
func nef.top.demo.nf (slots=2)
  %0 = call @args() :: []
  @1 = %0 :: int
  @0 = 1 :: int
  %1 = @0 + 2 :: int
  if overflow goto L0
  goto L1
  L0:
  _ = call @throw(10021, $13) :: [int,int]
  L1:
  _ = call @out_err(0) :: [int]
  _ = call @put_int(%1) :: [int]
  _ = call @out_err(0) :: [int]
  _ = call @put_nl() :: []
  ret
```

对应的输入是两行 `let a:int = 1` 与 `console.print(a + 2)`。

输出开头还会打印静态槽数、文本池条目与入口函数名，文本池逐条列出；上面的示例只截取了函数那一部分。

这个命令通常在两种情况下使用：想知道一条语句被拆成了哪几步；或者怀疑某处的生成结果与预期不符，需要直接查看发出的指令。

## 编译器自己的退出码

| 情况 | 退出码 | 消息输出位置 |
| --- | --- | --- |
| 检查通过、执行成功、产物生成成功 | `0` | 标准输出 |
| 程序有问题（检查报错、生成拒绝、文件读不到） | `1` | 标准错误 |
| 命令行用法不对（没给参数、子命令认不出、没给文件名） | `2` | 标准错误 |

编译器报的错和程序运行期抛的错是两类不同的错误：前者程序根本没开始运行，后者写在错误码表里（`10000` 往上归语言），可以在 `catch` 里捕获。两边都列在[错误信息索引](/tools/060_errors)。

## 程序的退出码

| 程序结束方式 | 返回操作系统的数值 | 消息输出位置 |
| --- | --- | --- |
| 顶层从第一行执行到最后一行 | `0` | 无输出 |
| 抛出的错误始终没有被捕获 | `1`，屏幕上打印一行 `出错了（10031）：下标越界` | 标准输出 |
| 调用层次过深，耗尽栈空间 | `1`，屏幕上打印一行 `出错了（10093）：调用套得太深，栈用完了` | 标准输出 |
| 程序自己调用 `exit (错误码, 说明)`，码在 `0` 到 `9999` 之内 | 括号里的数值 | 标准输出 |
| `exit` 的码写成 `10000` 往上 | 编译期拒绝，程序不会开始运行 | 不适用 |

上表中的几条错误消息由语言打印，都走标准输出，与 `console.print` 在同一条流上。程序自己输出的内容有两个去处：`console.print` 走标准输出，`console.print_error` 走标准错误（见[屏幕输出与输入](/stdlib/045_console)）。

把标准输出重定向进文件时，提示与进度走标准错误，就不会混入这个文件。

程序自己使用的码写在 `0` 到 `9999`，`10000` 往上由语言的内置错误码占用；超出这个范围时编译器当场拒绝，`exit` 与 `throw` 适用同一条规则。`exit (0, "跑完了")` 是这条规则允许的写法：打印一句话，再正常结束。

`exit` 不返回 `0`：要正常结束，就让顶层代码从第一行执行到最后一行。

## 生成阶段的边界

有三种写法会在检查阶段就报出来，不需要等到生成阶段：整个容器装箱、盒子再装一次，以及把文本交给 `number.to_string`。报的是下面三句：

| 写法 | 报错原文 |
| --- | --- |
| 整个容器装箱：`list`、`dict`、`hashset` 都算，如 `xs as object` | `list<int> 装不进盒子：盒子只装 class、struct 和值类型，要混装就一个一个装进去` |
| 盒子再装一次：`o as object`，`o` 本来就是盒子 | `object 不必再装箱：它已经在盒子里，直接用它就行` |
| 文本交给 `number.to_string`：`number.to_string("12")` | `number.to_string 不接 string：文本本来就是文本，接进来只会白拷一份` |

这三句都在检查阶段报出，退出码 `1`，报错位置精确到行与列。

盒子装 `class`、`struct` 与值类型。要往 `list<object>` 里放一段文本，先把它包进一个 `class` 再装箱。

另外两类问题容易被误算到生成阶段，它们都在**检查阶段**就报，不需要等到生成：

- 函数参数的默认值只能写字面量、顶层 `const` 的名字，以及这两者的算术运算。默认值写成变量（`method f(a:int = n)`）或函数调用（`f(a:int = g())`）时，都在参数声明处报错。
- `regular_expression` 的式子可以来自变量与拼接，编译期无法确定它的结果，因此式子写错要到运行时才报，抛出的错误号是 10071。

脚本在部署前分两步检查更稳妥：先 `nf check`，再 `nf build`，两步都通过才说明程序确实能运行。
